## Что это

Сервис бронирования звонков в духе Cal.com: Владелец публикует типы событий, Гости выбирают тип, свободный слот и записываются без регистрации.

**Развёрнутый сервис (деплой предыдущего проекта):** https://call-booking-0n46.onrender.com/

> На бесплатном плане Render первый заход после простоя может занять до минуты — сервис просыпается.

## Сценарии

**Гость**

1. Открывает каталог типов событий (`/book`) и выбирает нужный.
2. Выбирает дату и свободный слот в календаре (`/book/:id`).
3. Заполняет форму с именем и email (`/book/:id/form`).
4. Видит подтверждение брони (`/book/:id/done`). Занятый слот второй раз забронировать нельзя.

**Владелец** (`/admin`)

- Создаёт, редактирует и удаляет типы событий.
- Смотрит список предстоящих бронирований.

## Стек и структура

TypeScript, pnpm workspace, Node >= 24.21 (см. `.nvmrc`).

- `apps/api` — Fastify 5; маршруты под префиксом `/api`, хранилище в памяти.
- `apps/web` — React 19 + Vite.
- `packages/contract` — TypeSpec-контракт и сгенерированный `openapi.yaml`.
- `packages/api-client` — типизированный SDK, сгенерированный из OpenAPI.
- `e2e` — Playwright-тесты против собранного приложения.

## Запуск локально

```bash
pnpm install
pnpm dev
```

API стартует на порту 3000, web (Vite) — рядом; Vite проксирует `/api` на API.

### Docker

В Docker один контейнер: API раздаёт собранный фронтенд и отдаёт `index.html` для неизвестных GET вне `/api`.

```bash
pnpm docker:build
pnpm docker:run   # http://localhost:3000
# или на другом порту
docker run --rm -e PORT=10000 -p 10000:10000 ai-for-developers-project-387:local
```

## Контракт: TypeSpec → OpenAPI → SDK

Источник правды об API — `packages/contract/main.tsp`. Цепочка: TypeSpec → `packages/contract/openapi.yaml` → `packages/api-client/src/schema.d.ts` (типы SDK). Сервер читает `openapi.yaml` в рантайме (fastify-openapi-glue), отдельных серверных файлов нет.

Порядок изменения контракта:

1. Правим `packages/contract/main.tsp`.
2. Запускаем `pnpm generate` — пересобирает `openapi.yaml` и типы SDK одной командой.
3. Подгоняем `apps/api` и `apps/web` под новые типы.
4. Коммитим сгенерированные файлы вместе с изменением.

`pnpm generate:check` — `generate` + `git diff --exit-code` по сгенерированным файлам; запускается в CI перед `pnpm check` и падает, если артефакты устарели. В Docker-сборке `pnpm generate` не запускается.

## Тесты

- `pnpm check` — все проверки CI: format → lint → typecheck → test (Vitest) → build.
- `pnpm test:e2e` — Playwright против собранного приложения. Один раз нужен `pnpm --filter e2e exec playwright install chromium`. С `E2E_BASE_URL` тесты бьют по уже запущенному приложению.

В CI (`.github/workflows/ci.yml`):

- `check` — `pnpm generate:check` и `pnpm check`;
- `docker` — сборка образа и smoke-тест контейнера;
- `e2e` — Playwright против Docker-образа.

## Деплой на Render

Конфигурация — Blueprint `render.yaml` в корне: один web service, runtime Docker (`Dockerfile` из корня), план free, автодеплой из `main`, health check `/api/health`.

1. В Render: **New → Blueprint**, выберите этот репозиторий.
2. Проверьте переменные `OWNER_TZ` и `OWNER_NAME` (значения по умолчанию заданы в `render.yaml`).

`PORT` не задаётся: Render передаёт его сам, сервер читает его из окружения.

## Ограничения

- Данные хранятся в памяти и теряются при перезапуске и засыпании бесплатного плана Render ([ADR-0001](docs/adr/0001-in-memory-storage.md)).
- Авторизации нет по ТЗ: админка `/admin` и админские эндпоинты (`/api/event-types` для записи, `/api/admin/bookings`) доступны любому, кто знает URL.

## Агент в GitHub

В репозитории работают четыре агентных воркфлоу (`.github/workflows/opencode*.yml`) на базе [anomalyco/opencode](https://github.com/anomalyco/opencode):

| Воркфлоу                  | Событие / команда                                                                                  | Кто может вызвать                                          | Модель и почему                                                              | Права                                                     | Что создаёт                                                         | Где смотреть прогоны                                                                                          |
| ------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `opencode.yml`            | комментарий `/oc ...` в issue или PR (`issue_comment`, `pull_request_review_comment`, `[created]`) | OWNER / MEMBER / COLLABORATOR (автор комментария)          | `opencode/kimi-k3` — агент правит код по запросу, нужна сильная модель       | `id-token: write`, `contents: read`                       | ответы в комментариях; по запросу — коммиты и PR                    | [прогоны](https://github.com/ksv2005/ai-for-developers-project-387/actions/workflows/opencode.yml)            |
| `opencode-triage.yml`     | новый issue (`issues`, `[opened]`)                                                                 | OWNER / MEMBER / COLLABORATOR (автор issue)                | `opencode/deepseek-v4.1-flash` — текстовый разбор без правок, дешёвая модель | `id-token: write`, `contents: read`                       | один комментарий с разбором issue и рекомендуемым лейблом           | [прогоны](https://github.com/ksv2005/ai-for-developers-project-387/actions/workflows/opencode-triage.yml)     |
| `opencode-review.yml`     | `pull_request`: `opened`, `reopened`, `ready_for_review` (без `synchronize`)                       | автор недрафтового PR из ветки этого репозитория (не форк) | `opencode/kimi-k3` — ревью кода, нужна сильная модель                        | `contents: read`, `pull-requests: write`, `issues: write` | ревью PR: комментарии к строкам и общий вывод                       | [прогоны](https://github.com/ksv2005/ai-for-developers-project-387/actions/workflows/opencode-review.yml)     |
| `opencode-lighthouse.yml` | `schedule` (ежедневно в 03:00 МСК) и `workflow_dispatch`                                           | расписание; вручную — участник с правом запуска workflow   | `opencode/deepseek-v4.1-flash` — отчёт по готовой сводке, дешёвая модель     | `id-token: write`, `contents: read`, `issues: write`      | артефакт `lighthouse-report` и issue/комментарий «Lighthouse-отчёт» | [прогоны](https://github.com/ksv2005/ai-for-developers-project-387/actions/workflows/opencode-lighthouse.yml) |

**Защита от петель.** Триггеры подписаны узко: `types: [created]` для комментариев и `types: [opened]` для issues, а не любые изменения. Во всех четырёх воркфлоу в условии job'а стоит фильтр `!endsWith(github.actor, '[bot]')`, а вызов по комментарию ограничен командой `mentions: '/oc'`. Поэтому ответы самого агента (он пишет как бот) и issue, созданные токеном `GITHUB_TOKEN` (события от него не запускают воркфлоу), новых прогонов не порождают.

**Кто может звать агента.** Только владелец и коллабораторы: условие `author_association` пропускает лишь OWNER / MEMBER / COLLABORATOR (в `/oc` — автора комментария, в триаже — автора issue). В авторевью форки пропускаются: условие `head.repo.full_name == github.repository` оставляет только PR из веток этого репозитория.

**Права.** У каждого воркфлоу свой минимальный набор. У lighthouse — `issues: write`, потому что агент пишет отчёт только в issue через `GITHUB_TOKEN`; `contents: read` хватает для checkout, а `pull-requests` не нужен вовсе: мусорный PR #17 открыл не токен воркфлоу, а токен GitHub App из action'а, и permissions воркфлоу на него не влияют — поэтому вывод Lighthouse добавлен в `.gitignore` (`lighthouse/`), чтобы агенту нечего было коммитить. У review — `pull-requests: write` и `issues: write`, иначе агент не сможет оставить ревью и комментарии; `id-token` там не нужен, потому что при `use_github_token: true` action работает через `GITHUB_TOKEN`, а не через App. У `/oc` и триажа агент отвечает через токен App самого action'а, поэтому от воркфлоу нужны только `contents: read` и `id-token: write`.

**`share: false`.** Репозиторий публичный: при включённом `share` action публикует ссылку на полную сессию агента (промпт, контекст, ход рассуждений), и её может открыть любой. Поэтому во всех шагах `anomalyco/opencode/github` стоит `share: false` — сессии не уходят наружу, а логи остаются в прогоне Actions.

**Расходы.** Ключ `OPENCODE_API_KEY` выдан с лимитом программы, поэтому дорогая модель (`opencode/kimi-k3`) стоит только там, где правится и ревьюится код (`opencode.yml`, `opencode-review.yml`), а триаж и Lighthouse работают на дешёвой `opencode/deepseek-v4.1-flash`. Авторевью сознательно без `synchronize`, чтобы каждый пуш в PR не жёг бюджет, — повторный разбор вызывается reopen'ом PR. У lighthouse стоит `timeout-minutes: 20`, чтобы зависший агент не ел минуты и бюджет.

**Известные ограничения.** Action проверяет права `github.actor`, поэтому события от бота (например, комментарии самого агента) падают с ошибкой доступа — повторное ревью PR агента запускает человек через reopen PR. В schedule-режиме у агента нет контекста события, и для работы с issues ему нужен явный `GH_TOKEN` — он передан в env шага lighthouse.

### Самооценка работы с агентом

**С первого прохода:**

- #12 — авторевью нашло настоящую проблему в собственном воркфлоу (нет фильтра для форков).
- #16 — ночной Lighthouse-отчёт: оценки, находки с файлами и путём исправления, отделены эффекты хостинга; по находке заведён #18.

**Потребовали итераций:**

- #3 → PR #9: разбор предложил дублирующую проверку в сервисе (422) — убрана в постановке; коммит агента нарушил формат (`fix: запрет имён…`) — правило в AGENTS.md уточнено, заголовок исправлен при мерже.
- #11 → PR #13: заголовок PR на русском и граница `<` вместо `<=` — исправлены агентом по общему комментарию и комментарию к строке, отдельным коммитом в ту же ветку.
- Авторевью: 403 при правах только на чтение; фильтр по author_association отсёк бы PR агента; action падает на событиях от бота.
- Lighthouse: агент завис без GH_TOKEN (добавлен токен и timeout); action закоммитил отчёт в мусорный PR #17 (вывод в .gitignore).
- Бюджет ключа исчерпан за день — авторевью ограничено, дешёвая модель для триажа и Lighthouse.

**Вывод:** агент быстро даёт точный разбор и небольшие правки, но постановку, формат коммитов, права и границы задачи проверяет человек; основные итерации ушли на инфраструктуру GitHub Actions, а не на код.
